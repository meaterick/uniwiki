# UniWiki 개발 명세서 v0.3

2026-11-27 · 상세 설계 및 출시 검증 보강

UniWiki는 대학별 학교생활 정보를 학생들이 함께 작성하고 갱신하는 위키다. 비회원도 여러 대학의 공개 정보를 조회할 수 있고, 소속이 승인된 회원은 자기 대학의 일반·교수 문서를 작성하고 편집할 수 있다.

## 1. 출시 범위

| 단계 | 범위 |
| --- | --- |
| 첫 공개 | 대학 목록·홈, 공개 문서 조회, 대학별·통합 검색, 가입 및 수동 학생 인증, Markdown 작성·편집, 이미지·외부 영상 링크, 수정 이력, 욕설 필터, 기본 신고·운영자 검토 |
| 후속 | 개인 문서·프로필, 하트·아직 유용해요·해시태그, 문서 랭킹, 잼컨 게시판, 학교 정보 크롤링, OCR·학교 이메일 인증 검토 |
| 보류 | 누적 신고에 따른 계정 차단 기능 및 정기 이의 심사 |

## 2. 기술과 협업

| 담당자 | 역할 | 책임 |
| --- | --- | --- |
| 인찬 | 검색·배포 | 제목·본문 검색, 대학 범위 필터, 한국어 검색 품질, OCI 배포 |
| 연호 | 백엔드·보안 | Node.js/Express API, 가입 심사, 권한 검증, 업로드·신고·감사 이벤트 |
| 재상 | DB 개발·관리 | MySQL 스키마와 마이그레이션, 이미지·문서 이력·백업, 후속 크롤링 데이터 적재 |
| 다인 | 프론트엔드 | React 화면, Markdown 에디터와 미리보기, 검색·신고 UI, 접근성·오류 상태 검수 |

GitHub Issues로 기능을 관리하고 PR로 병합한다. 프론트엔드 구현을 포함해 AI를 활용하며, 팀원이 동작·예외 처리·권한을 코드 리뷰한다. PR에 변경 목적과 확인 방법을 남긴다. 도입하는 오픈소스와 아이콘·폰트의 라이선스 및 배포 고지 조건을 확인한다. 실제 가입 증빙, 회원 데이터, 서비스 비밀값은 AI 도구에 입력하지 않는다.

## 3. 가입과 권한

- 이메일, 이름, 대학, 닉네임을 필수로 받는다. 가입 화면에서 나이와 성별은 수집하지 않는다. 공개 작성자 표시는 닉네임을 사용한다.
- 재학증명서, 입학증명서, 합격증 등의 증빙으로 운영자가 신청 이름과 대학을 대조한다. 이메일 인증은 후속 검토 사항이다. 신청 상태는 심사 대기, 승인, 반려로 관리한다. 반려 시 사유를 안내하고 재제출을 받는다.
- 증빙은 공개 게시 이미지와 접근 경로를 분리한다. 신청자와 심사 담당자만 접근 가능하게 하고 심사 직후 승인·반려와 관계없이 원본을 삭제한다. 심사 결과, 처리 시각, 처리자는 남긴다. 원본은 일반 DB 백업·로그에 포함하지 않는다. 일시 오류로 삭제가 실패하면 재시도하고 운영자에게 표시한다.
- 비회원과 가입 심사 중 사용자는 여러 대학의 공개 문서를 조회·검색할 수 있다. 해당 대학의 승인 회원만 그 대학의 일반·교수 문서를 생성·편집한다. 모든 대학의 승인 회원은 공개 콘텐츠를 신고할 수 있다.
- 후속 개인 문서 기능은 가입 심사에서 증빙과 이름의 일치를 확인한 결과를 활용한다. 계정당 본인 문서 한 개를 제안한다. 본인 전용 영역은 본인만 편집하며, 하단의 다른 회원 작성 글은 별도 레코드로 관리한다. 하단 글 작성 범위와 프로필 공개 필드는 기능 착수 시 확정한다.

## 4. 첫 공개 요구사항

| ID | 요구사항 | 인수 기준 |
| --- | --- | --- |
| W-01 | 대학별 홈·목록·문서 조회 | 비회원이 두 대학의 공개 문서를 열 수 있다. 대학이 다르면 같은 제목을 사용해도 각 문서가 올바르게 조회된다. |
| W-02 | Markdown 생성·편집·미리보기 | 해당 대학 승인 회원이 일반·교수 문서를 저장할 수 있다. 타 대학 회원의 쓰기는 서버에서 거절한다. 문서와 미리보기 모두 같은 렌더링 및 정화 규칙을 적용한다. |
| W-03 | 최초 버전부터 이력 보관 | 편집 저장마다 버전이 추가된다. 같은 버전에서 동시 수정하면 뒤의 저장은 HTTP 409를 반환하고 입력을 보존한다. 이전 버전을 복구하면 새 버전으로 저장한다. |
| W-04 | 이미지 및 외부 영상 링크 | 서버가 이미지 형식과 크기를 검사한 뒤 리사이즈·재인코딩하고, 메타데이터가 제거된 처리본을 MySQL에 저장한다. 영상은 외부 URL만 저장하며 허용 서비스는 임베드한다. |
| W-05 | 대학별·전체 검색 | 제목과 본문에서 한국어 검색이 가능하고, 선택한 대학 범위를 적용한다. 비공개 콘텐츠가 결과와 미리보기에 노출되지 않는다. 태그 검색은 태그 기능과 함께 추가한다. |
| M-01 | 욕설 필터 | 서버가 탐지한 저장본은 작성자 전용으로 저장한다. 기존 공개 문서의 수정안이 탐지되면 마지막 공개본을 제공한다. URL 직접 접근과 이력·검색에서도 동일한 공개 상태를 적용한다. 작성자는 탐지된 저장본을 수정할 수 있다. |
| M-02 | 신고 | 인증 회원이 공개 콘텐츠를 신고할 때 사유와 선택 설명을 받는다. 같은 사용자·대상 조합은 한 번만 집계한다. 서로 다른 인증 회원의 신고 3건부터 운영자 검토 목록에 한 번 등록한다. 신고 수만으로 콘텐츠를 자동 삭제하지 않으며 운영자는 약관에 따라 처리하고 근거를 기록한다. |

## 5. 후속 요구사항

| 기능 | 동작 |
| --- | --- |
| 프로필 | 본인만 개인정보·외부 링크 영역을 수정한다. 다른 회원의 하단 글은 작성자와 공개 상태를 따로 저장한다. |
| 하트 | 계정당 문서별 한 번 등록하거나 취소한다. 1~9개는 아이콘 1개, 10~99개는 2개, 100개 이상은 3개를 겹친다. 0개는 기본 버튼을 표시한다. |
| 아직 유용해요 | 하트와 독립적인 반응을 기록하고, 일정 기간 안에 유용하다는 반응이 있었던 문서를 필터링한다. 유효 기간은 추후 확정한다. |
| 태그·랭킹 | 문서 상단에 해시태그를 표시하고 태그 검색을 지원한다. 하트 수·누적 유효 방문·개인별 방문을 랭킹에 사용한다. 방문 중복 제거 기준, 비회원 방문 반영, 가중치는 추후 확정한다. |
| 교내 잼컨 게시판 | ‘진짜에요’와 ‘가짜에요’ 중 계정당 한 표를 집계한다. 서로 다른 계정의 ‘가짜에요’ 5표부터 게시글을 임시 숨기고 운영자 검토에 등록한다. 운영자가 확인 후 삭제하거나 복원한다. |
| 학교 정보 크롤링 | 공식 학교 페이지의 공개 자료를 대상으로 수집 범위를 정한다. 출처 URL과 수집일을 기록하고 중복을 제거한다. 수집 결과는 검토 후 공개한다. |

## 6. 데이터와 API 초안

| 데이터 | 설계 |
| --- | --- |
| 대학·계정 | `universities`, `users`, `memberships`, `verification_requests`. 신청과 승인 상태 및 이름 일치 결과를 기록한다. |
| 문서·이력 | `documents`, `document_revisions`. 대학 내 문서 식별자와 문서별 버전 번호에 고유 제약을 둔다. 새 버전 삽입과 공개 참조 갱신을 한 트랜잭션에서 처리한다. |
| 이미지 | `media`. MIME, 크기, 해상도, 처리본 BLOB을 저장하고 연결 문서의 공개 상태를 조회에 적용한다. |
| 신고·운영 | `reports`, `moderation_actions`, `audit_events`. 신고 대상·사유·처리 상태와 운영자 결정 근거를 기록한다. |
| 후속 | `profiles`, `profile_posts`, `tags`, `document_tags`, `document_reactions`, `document_visits`, `campus_posts`, `campus_votes`. 반응·투표 중복은 고유 제약으로 방지한다. |

| 영역 | REST API |
| --- | --- |
| 가입·심사 | `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/verifications`, `POST /api/admin/verifications/{id}/decisions` |
| 대학·문서 | `GET /api/universities`, `GET/POST /api/universities/{id}/documents`, `GET/PATCH /api/documents/{id}` |
| 이력·복원 | `GET /api/documents/{id}/revisions`, `POST /api/documents/{id}/restore` |
| 검색·이미지 | `GET /api/search`, `POST /api/media`, `GET /api/media/{id}` |
| 신고·검토 | `POST /api/reports`, `GET /api/admin/reviews`, `POST /api/admin/moderation-actions` |

목록과 검색에는 페이지네이션을 적용한다. 편집 요청에는 기준 버전 ID를 포함한다. 서버는 대학·소유권·심사 상태를 검사하고 프론트에서 구분할 수 있는 오류 코드를 반환한다.

## 7. 운영과 출시 검증

- 배포 환경은 OCI다. 초기 후보인 1GB·1코어 환경에서는 검색과 이미지 전처리를 함께 수행하며 응답시간·메모리·디스크 증가량을 확인한다.
- 접근·오류·감사 로그는 장기 보관한다. 로그를 회전·압축하고 OCI 디스크 사용량에 맞춰 외부 저장소로 이관한다. 비밀번호, 토큰, 증빙 원본, 요청 본문은 기록하지 않는다.
- 문서 이력은 최초부터 보존한다. 장애 대응용 DB 백업은 별도로 보관하고 첫 공개 전에 문서·이력·이미지 복원 시험을 한다. 백업 주기와 보관 개수는 미정이다.
- 출시 전 승인·반려·증빙 삭제, 대학 간 공개 조회와 편집 차단, 동시 편집, 신고 2건에서 3건으로의 전환, 숨김 콘텐츠 접근 제한, DB 복원을 검증한다.

## 8. 가입·학생 인증 상세 설계

이 절과 9~12절은 첫 공개 구현을 위한 설계 초안이다. **결정 필요**로 표시한 항목은 13절에서 추적한다. 1~7절의 인터뷰 확정 사항을 기준으로 구현한다.

| 상황 | 처리 규칙 |
| --- | --- |
| 가입 | 이메일·이름·대학·닉네임을 검증한다. 이메일 중복은 DB 고유 키로 검사한다. 비교용 정규화 규칙, 로그인 수단, 이메일 변경·계정 복구 절차는 결정 필요다. |
| 증빙 제출 | 신청서의 이름·대학과 증빙에 표시된 정보를 대조한다. 합격증은 제출할 수 있으며, 합격생 승인 후 편집 권한과 표시 문구는 결정 필요다. |
| 승인·반려 | 한 대기 신청에는 최종 결정을 한 번만 적용한다. 승인 시 해당 대학 소속을 활성화하고 반려 시 재제출을 허용한다. 재제출은 이전 결정을 덮어쓰지 않고 새 신청으로 저장한다. |
| 증빙 삭제 | 심사 결정과 삭제 작업 등록을 같은 DB 트랜잭션에 기록한다. 커밋 직후 삭제를 시작하고 원본 접근 권한을 종료한다. 삭제 상태는 심사 상태와 별도로 `PENDING → DELETED` 또는 `FAILED`로 표시한다. 삭제 실패 시 재시도하며 이미 삭제된 파일은 완료로 처리한다. |
| 미심사·학교 변경 | 미심사 증빙의 만료 기간, 소속 변경 허용 여부와 효력 시점은 결정 필요다. API는 매 쓰기 요청에서 유효한 소속을 확인한다. |
| 개인 문서 연결 | 이름은 증빙 대조에 사용하고 개인 문서 소유자는 계정 ID로 연결한다. 동명이인은 같은 대학에서도 별개 계정이다. |

## 9. 문서·이력·첨부 상태

**구현 제안.** 문서의 운영 상태와 버전의 공개 범위를 별도로 관리한다. 공개 버전이 없는 문서도 저장할 수 있으며, 목록과 검색에는 공개 상태의 문서 중 공개 버전이 있는 문서만 표시한다.

| 상황 | 저장 및 조회 결과 |
| --- | --- |
| 정상 생성·편집 | 새 버전을 저장하고 현재 공개 버전을 갱신한다. 편집 기준 버전 확인, 버전 삽입, 공개 버전 갱신을 한 트랜잭션에서 처리한다. |
| 첫 버전 필터 탐지 | 작성자 전용 버전을 저장한다. 문서의 공개 버전 참조는 비어 있으며 문서 상세·검색·공개 이력에서 조회할 수 없다. |
| 수정 버전 필터 탐지 | 작성자 전용 버전을 저장하고 마지막 공개본을 유지한다. 저장 응답으로 작성자에게 버전 공개 범위와 탐지 사유 코드를 전달한다. |
| 작성자 전용 버전 재편집 | 재편집할 버전 ID와 사용자가 편집을 시작할 때 확인한 공개 버전 ID를 함께 전송한다. 서버는 작성자 권한을 확인하고, 그 사이 공개 버전이 바뀌면 입력을 유지할 수 있도록 충돌 응답을 반환한다. |
| 운영자가 문서 전체를 숨김 | 공개 상세·검색·공개 이력에 숨김을 적용한다. 일반 편집이나 버전 복원으로 운영상 숨김 상태를 해제할 수 없다. 운영자가 공개를 복구할 경우 조치 근거와 처리자를 기록한다. |
| 버전 복원 | 접근이 허용된 이력의 본문을 새 버전으로 저장한다. 새 버전에 필터 및 공개 정책을 다시 적용한다. 첫 출시에서 일반 편집자에게 복원을 허용할지는 결정 필요다. |

이미지 원본은 전처리 후 폐기하고 MySQL에는 처리본을 저장한다. **구현 제안**은 아래와 같다.

- 업로드 직후 문서에 연결되기 전까지는 작성자만 접근한다. 문서 저장 시 해당 버전의 본문에서 실제 참조하는 이미지 ID와 서버에 연결하는 이미지 ID가 일치해야 한다.
- 접근 가능한 버전이 하나라도 해당 이미지를 참조하면 그 사용자가 이미지를 조회할 수 있다. 운영자가 이미지 자체를 숨겼다면 모든 버전에서 접근을 제한한다. 공개 연결이 없어지면 캐시에서도 공개 응답이 계속 제공되지 않도록 처리한다.
- 어떤 버전에도 연결되지 않은 업로드는 보관 기간이 지난 뒤 정리한다. 현재 본문에서 빠진 이미지도 보존 대상 버전이 참조하면 유지한다.
- 요청 파일 크기, 최대 픽셀 수, 처리 결과 크기, 문서당 첨부 수, 동시 처리 수, 임시 업로드 보존 기간은 OCI 검증 후 정한다.

## 10. 신고와 운영 조치

서로 다른 인증 회원의 신고 **3건**부터 일반 운영자 검토 목록에 등록한다는 확정 정책을 적용한다.

- **제안.** 본문 신고는 문서 ID·신고 시점의 공개 버전 ID·사유·신고자를 보관하고 같은 버전에 대한 신고끼리 집계한다. 버전 ID가 대상 문서에 속하는지 확인한다. 문서 전체를 대상으로 하는 사유를 별도로 둘지와 버전별 집계 적용 여부는 팀에서 확정한다.
- 신고 등록과 검토 건 생성은 동시 요청에도 같은 회원 신고나 검토 건이 중복 생성되지 않도록 처리한다. 운영 화면에는 신고된 버전과 현재 공개 버전, 각각의 공개 상태를 표시한다.
- **제안.** 검토 건은 `OPEN → RESOLVED / DISMISSED`로 관리하고 처리자·근거·시각·조치 대상을 기록한다. 버전 숨김, 문서 전체 숨김, 복구는 각각 별도 조치로 기록한다. 현재 공개 버전을 숨겼을 때 이전 버전으로 자동 전환할지는 결정 필요다.
- 개인정보 노출 등의 신고를 1건부터 별도 검토할지 결정한다. 예외가 확정되기 전에는 일반 3건 기준을 적용한다.

## 11. API·DB 계약 초안

### API 요청과 응답

`PATCH /api/documents/{id}` 요청 예시

```json
{
  "baseRevisionId": 42,
  "expectedPublicRevisionId": 42,
  "markdown": "# 학교 도서관",
  "attachmentIds": []
}
```

`baseRevisionId`는 편집을 시작한 버전이다. `expectedPublicRevisionId`는 편집 시작 시 확인한 공개 버전이며 공개본이 없으면 `null`이다. Markdown은 문자열, 첨부 목록은 이미지 ID 배열로 받는다. 필드별 길이·첨부 수 한도는 출시 전에 확정한다.

| 결과 | 응답 계약 |
| --- | --- |
| 공개 버전 저장 | `200`, `revisionId`, `visibility: PUBLIC`, `publicRevisionId` |
| 작성자 전용 저장 | `200`, `revisionId`, `visibility: AUTHOR_ONLY`, `publicRevisionId` 또는 `null`, `reasonCode: CONTENT_FILTERED` |
| 로그인 필요·쓰기 권한 없음 | 각각 `401 AUTH_REQUIRED`, `403 WRITE_FORBIDDEN`. 읽기 권한이 없는 비공개 리소스는 `404`로 응답한다. |
| 공개 버전 충돌 | `409 REVISION_CONFLICT`, 접근 가능한 현재 공개 버전 ID. 프론트는 편집 내용을 보존하고 비교·재편집 흐름을 제공한다. |
| 입력 오류 | `422 VALIDATION_ERROR`, 필드별 오류. 파일 요청이 크기 제한을 초과하면 `413`으로 응답한다. |

신고 API에는 대상 문서, 대상 버전, 신고 사유 코드와 선택 설명을 보낸다. 기준안은 `201`로 신고를 접수하며 동일 요청의 재시도에는 기존 신고 ID를 반환한다. 목록·검색은 페이지 입력, 기본 정렬, 동점 시 ID 기준 정렬 및 다음 페이지 유무를 공통 규약으로 정의한다.

### 주요 제약

| 데이터 | 구현 제안 |
| --- | --- |
| 계정 | `users(normalized_email)` 고유. 학생 인증 신청과 결과는 사용자·대학 ID에 연결한다. |
| 문서·버전 | `documents(university_id, slug)`, `document_revisions(document_id, revision_number)` 고유. 공개 버전 참조는 같은 문서의 공개 가능 버전이어야 한다. |
| 버전 첨부 | `revision_media(revision_id, media_id)` 고유. 문서 버전과 이미지의 연결을 보존한다. |
| 신고·검토 | 버전별 집계 채택 시 `reports(reporter_id, revision_id)`, `review_cases(revision_id)` 고유. 신고·검토 등록과 집계 기준 판정을 트랜잭션으로 처리한다. |

## 12. 운영 절차와 출시 검증

- **배포.** 마이그레이션을 검증 환경에 먼저 적용한다. 운영 적용 전 복구 지점을 확인하고 실패 시 후속 배포를 중단한다. 마이그레이션 유형별 롤백 또는 복원 절차를 릴리스에 기록한다.
- **장기 로그.** 접근·오류·감사 로그를 회전·압축하고 외부 저장소 이관 성공을 확인한 뒤 로컬 보관분을 정리한다. 이관 실패 시 재시도하고 디스크 경보를 발생시킨다. 로그와 백업의 교차 검증에 합성 데이터를 사용한다.
- **복구.** 백업 주기·보관 개수, 허용 데이터 손실 시간(RPO), 목표 복구 시간(RTO)을 정한다. 별도 환경에 복원해 문서·버전·이미지의 참조와 운영 조치를 검증한다. 복구 지점 이후에 적용된 숨김·삭제 조치가 있다면 공개 재개 전에 반영한다.

| 시나리오 | 통과 기준 |
| --- | --- |
| 동시 편집 | 같은 공개 버전을 기준으로 두 공개 수정 요청을 보내면 한 건만 반영되고 다른 편집 내용은 유지된다. |
| 비공개 버전과 이미지 | 필터에 걸린 최초 작성본과 해당 버전에서만 참조하는 이미지는 작성자 외에 직접 URL·검색·공개 이력에서 노출되지 않는다. |
| 신고 임계치 | 신고 2건 상태에서 여러 인증 회원이 동시에 신고해도 운영자 검토 건이 한 건만 생성된다. 동일 계정의 재시도는 집계를 늘리지 않는다. |
| 증빙 삭제 실패 | 삭제 오류를 발생시켜도 심사 결과는 유지되고 증빙 접근은 종료된다. 재시도 완료를 운영 화면에서 확인할 수 있다. |
| 장애 복구 | 복원한 환경에서 공개 문서와 허용된 이미지가 조회되고 숨겨진 문서·버전·이미지는 기존 공개 제어를 따른다. |
